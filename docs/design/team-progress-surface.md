# 团队进度说明图

模式：Read。适用范围：独立的 `team-map/` GitHub Pages 页面。

## 已确认方向

- 使用现有团队地图的暖纸、深绿文字、细线和圆角语言，按首月 MVP 的阻塞与交接顺序重排。
- 首页以手动总进度与当前 P0 为阅读起点。初始进度为用户指定的 30%，主要来自开发工作，明确为估算。
- 六个环节：商品与内容准备、店铺运营、仓储发货、Shopify、顾客网站、客服售后；箭头说明资料怎样传递。Shopify 是软件工具，不是一个岗位。
- 首页点击进入详情后，任务、具体做法、例子和待定事项全部直接展示。商品准备页包含选品、内容与商品资料；运营页不再链接到另一个同名详情。保留地址、面包屑与浏览器返回，不使用折叠详情。
- 文案面向没有编程经验的读者：使用商品资料、库存数量、订单记录、发货、快递单号等具体说法。页面中的 P0 / P1 用白话解释先后顺序。
- 运营分两阶段：首版由锦晨、启航直接操作 Shopify、对接各方；流程跑顺并完成培训后，黄总公司接手日常运营。接手公司已确定，具体同事、权限和培训仍需落实。
- Shopify 详情单独解释三类资料、五条资料往来和人工操作边界；软件能力与本店实际完成状态分开。没有宣称仓库系统或 LINE 聊天已经自动同步。
- 商品与内容准备为 P0。红色表示 P0 未就绪，橙色表示 P1 未就绪，绿色表示确认已就绪；没有确认记录时显示灰色待核实，并保留优先级标签。
- 至少一个完整商品供运营确认可以上架；首月以内部测试订单完成购买与支付测试、试发货、物流回填与售后演练。3–5 个成品品类为后续候选，不构成首件闭环门槛。
- 只读发布，由锦晨统一维护，不引入账号或后台。页面是团队说明与展示，不另设开发 Issue tracker。

## 当前实现

- 桌面：左侧六环节关系图，右侧验收、状态说明和确认规则。手机：总进度与 P0 优先，两列短环节及对应连接线；详情为单列、直接可读。
- 任务显示 `blocked`、`unknown`、`ready`。ready 需要交付人与接手人确认依据；没有依据的 ready 会回退显示待核实。
- 主体全部任务已确认 ready 时才整体转绿；总百分比由维护人单独更新，不按任务数量推算。

## 维护

1. 编辑 `team-map/progress.js` 的 `percent`、`updated`、`note` 更新首页进度及说明。百分比为 0–100 的人工估算。
2. 对任务维护 `status` 与 `evidence`。公开说明只记录必要确认结论，不写私人联系信息。负责人和交付标准在 `map.js` 的 `taskDefinitions` 中。
3. 如更改百分比，同步 `index.html` 内无 JavaScript 的默认进度与 noscript 提示。
4. 经 Issue / PR 确认合入 main，现有 Pages workflow 发布 `team-map/`。全体查看者读取发布后的同一份静态状态。

任务 ready 不自动证明实际支付配置、仓库位置或运营权限已落实；逐项确认依据才是判断来源。
